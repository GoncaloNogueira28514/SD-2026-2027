===============================================================================
1. RESUMO EM 10 LINHAS
===============================================================================

Na COMINDIR04 cada partição tinha um líder FIXO (PartitionLeader) e réplicas
passivas; se o líder caísse, as réplicas só SUSPEITAVAM e a partição ficava sem
ninguém a atribuir seq. Agora cada partição de dados p<k> é servida por um GRUPO
de 3 nós idênticos (PartitionNode), e qualquer um pode ser líder. Os nós ELEGEM o
líder por MAIORIA (2 de 3) num TERMO: um número que só cresce, é gravado em disco
e garante no máximo um líder por termo. Quando o líder falha, os seguidores
deixam de receber LOTEs, o prazo de eleição (aleatório, 6–12 s) expira e um deles
candidata-se. Um líder antigo que regresse vê um termo superior e demite-se; os
registos que escreveu e que o novo líder não tem são TRUNCADOS. Não há commit por
maioria: isso é uma limitação assumida (o sistema não é um CP completo).

3. COMO COMPILAR E EXECUTAR (Windows / Git Bash)
===============================================================================

Compilar (a partir de Sprints/E1-COMINDIR05):

  for p in no produtor processador; do (cd raft04-$p && javac -encoding UTF-8 -d out *.java); done

Executar (IPFS com Pubsub ativo; todos os processos na MESMA máquina e na MESMA
pasta de trabalho, de preferência uma pasta limpa por ensaio, p.ex. ensaio-a/):

  mkdir ensaio-a && cd ensaio-a
  # nove nós, por qualquer ordem:  PartitionNode <k> <i> [N=3] [api]
  java -cp ../raft04-no/out raft04.PartitionNode 0 1
  java -cp ../raft04-no/out raft04.PartitionNode 0 2
  java -cp ../raft04-no/out raft04.PartitionNode 0 3
  java -cp ../raft04-no/out raft04.PartitionNode 1 1      (… e assim para p1 e p2)
  # depois o processador e por fim o produtor
  java -cp ../raft04-processador/out raft04.AlarmProcessor 3
  java -cp ../raft04-produtor/out raft04.Producer 3
     > S02 20.1                (S02 e S05 pertencem a p1 com N=3)
     > rajada 300 10           (como antes: o mais depressa possível)
     > rajada 300 10 100       (NOVO 3.º argumento opcional: 100 ms entre leituras → ~30 s,
                                para dar tempo de provocar uma falha "durante a rajada")

Parâmetros (passar o MESMO valor a todos os processos):
  -Draft04.periodo=<ms>     Δ (2000)
  -Draft04.fator=<f>        TIMEOUT dos detetores = f×Δ (3)
  -Draft04.eleicaoMin=<ms>  (3Δ = 6000)      -Draft04.eleicaoMax=<ms> (6Δ = 12000)
  -Draft04.falha=<1..5>     falha deliberada do ponto 10 (só nos nós)

Provocar a falha de um nó (equivalente Windows de kill -9):
  echo "p1;n2;$(date +%s%3N)" >> falhas.txt; taskkill //F //PID <pid do java>
  O PID certo é o da JVM: "jps -m" mostra, por exemplo,
     12345 PartitionNode 1 2      → taskkill //F //PID 12345
  ATENÇÃO (verificado nos testes): no Git Bash, "kill -9 $!" NÃO mata o java.exe
  (mata só o processo intermédio do MSYS), e se o java for o lançador
  C:\Program Files\Common Files\Oracle\Java\javapath\java.exe, o PID desse
  lançador também não é o da JVM. Usar sempre jps + taskkill (ou o Gestor de
  Tarefas). Em Linux/macOS: kill -9 <pid> (também com o pid do jps).

Provocar uma partição de rede (ensaio 9(d)): na pasta de trabalho
  echo "isolar p1 n2 $(date +%s%3N)" >> particoes.txt; touch isolar-p1-n2
  … 30 s …
  echo "reparar p1 n2 $(date +%s%3N)" >> particoes.txt; rm isolar-p1-n2
  (o nó também regista ISOLAMENTO;p1;inicio / fim no seu ficheiro de eventos)

Análise no fim de cada ensaio:
  java -cp ../raft04-no/out raft04.RaftCheck 3 . falhas.txt
  java -cp ../raft04-no/out raft04.CausalCheck 3 .

Entre ensaios: a ficha manda apagar estado-* e no-*. Recomendo apagar TUDO
(ou usar outra pasta), porque o RaftCheck analisa a pasta inteira como um único
ensaio: um eventos-* de um ensaio anterior faria aparecer "termo diminuiu" no
arranque do ensaio seguinte (o termo volta a 0 porque o estado foi apagado).


===============================================================================
4. IMPLEMENTAÇÃO, CLASSE A CLASSE
===============================================================================

4.1 Wire
--------
- PERIODO_HB_MS (raft04.periodo, 2000), FATOR_TIMEOUT (raft04.fator, 3),
  VERIFICACAO_MS = 200, ELEICAO_MIN_MS / ELEICAO_MAX_MS (raft04.eleicaoMin/Max,
  por omissão 3Δ e 6Δ), GRUPO = 3. Retirado tudo o que se referia a inc.
- topicIn(k), topicData(k), topicElection(k) = "raft04-eleicao-p<k>".
- nodePort(k, i) = 7000 + 10k + i.
- isolated(k, i): true enquanto existir o ficheiro isolar-p<k>-n<i>. Simula uma
  partição de rede: o nó isolado não publica nem processa mensagens de raft04-p<k>
  e raft04-eleicao-p<k>, e o TCP de recuperação falha (como cliente lança
  IOException, como servidor fecha a ligação sem responder). raft04-in-p<k> NÃO é
  afetado (o produtor continua a alcançar os dois lados).
- FALHA (raft04.falha): seleciona a falha deliberada do ponto 10.

4.2 Mensagens: Batch, VoteRequest, VoteReply, SensorRecord
---------------------------------------------------------
- Batch: cabeçalho LOTE;termo;lider;endereço;porto;hb;ultimoSeq;ultimoTermo;n
  (9 campos). decode() valida que o número de linhas = n. decodeHeader() só lê a
  1.ª linha (o produtor não precisa dos registos).
- VoteRequest / VoteReply: encode()/decode() de PEDIDO_VOTO e VOTO.
- SensorRecord: passa a ter term. toLine() = seq;termo;sensor;temp;instante;L;V.
  sameEntry(o): mesmo seq e mesmo termo → "é o mesmo registo" (só o líder do termo
  t cria registos com termo t, e cada seq só uma vez nesse termo).
  reading() = "sensor@temperatura", usado pelo RaftCheck para reconhecer a mesma
  leitura com outro seq.

4.3 RecordFile
--------------
append, readAll, last, lastSeq, range (como antes) e rewrite(list): escreve um
ficheiro .tmp e substitui o original com Files.move(..., ATOMIC_MOVE). É usado na
truncagem: quem lê vê o ficheiro antigo ou o novo, nunca um ficheiro a meio.
Todos os métodos são synchronized (o servidor TCP lê o ficheiro enquanto o nó
pode estar a escrever).

4.4 RaftState (código da ficha, com 4 "interruptores" de falha)
---------------------------------------------------------------
Estado persistente: term, votedFor (0 = ainda não votou neste termo).
Estado volátil: role (SEGUIDOR/CANDIDATO/LIDER), leader, votes, deadline.
- Construtor: lê estado-p<k>-n<i>.txt se existir → um nó que reinicia retoma o
  mesmo termo e o mesmo voto. Sorteia o primeiro prazo.
- resetTimer(): deadline = agora + U[ELEICAO_MIN_MS, ELEICAO_MAX_MS]. Chamado no
  arranque, ao candidatar-se, ao conceder um voto e ao aceitar um LOTE válido.
- persist(): escreve "termo;votouEm" num .tmp e faz ATOMIC_MOVE.
- adoptTerm(t): termo superior observado → (DEMISSAO se era líder), TERMO a->b,
  term = t, votedFor = 0, papel = SEGUIDOR, leader = 0, persist().
- tick() (a cada 200 ms): se não for líder e o prazo expirou → term++, votedFor =
  self, persist(), papel = CANDIDATO, votes = {self}, novo prazo, CANDIDATO;
  devolve o termo (senão −1).
- onVoteRequest(cTerm, cand, cLastSeq, cLastTerm, meuLastSeq, meuLastTerm):
  adota cTerm se for maior; concede sse (1) cTerm == term, (2) votedFor ∈ {0, cand},
  (3) upToDate = cLastTerm > meu ou (igual e cLastSeq ≥ meu). Se conceder: grava e
  renova o prazo. Devolve (term, granted). Regista VOTO concedido/recusado.
- onVote(vTerm, voter, cand, granted): termo superior → adota e devolve false;
  ignora votos de outro termo/papel/candidato/recusados; junta o voto; se
  votes.size() > G/2 (= 2 com G = 3) → LIDER e devolve true (uma só vez).
- onBatch(bTerm, bLeader): termo inferior → false (líder obsoleto); superior →
  adota; se ainda for LIDER no mesmo termo → ERRO "dois lideres" (impossível pelas
  regras); senão passa a SEGUIDOR (um candidato reconhece o líder), NOVO_LIDER se
  mudou, renova o prazo, true.
- termIfLeader(): term se for líder, senão −1. É ISTO que o nó consulta, dentro da
  sua secção sincronizada, antes de atribuir um seq.

4.5 PartitionNode (PartitionNode <k> <i> [N] [api])
---------------------------------------------------
ARRANQUE (construtor + iniciar()):
  1. lê no-p<k>-n<i>.txt para a lista em memória "log" (log.get(s-1) = registo s)
     → ultimoSeq = log.size(), ultimoTermo = termo do último registo;
  2. cria o RaftState com estado-p<k>-n<i>.txt (seguidor, termo gravado);
  3. regista ARRANQUE;p<k>;termo;votouEm;ultimoSeq;ultimoTermo;…;
  4. abre o ServerSocket em Wire.nodePort(k,i) (antes de subscrever);
  5. subscreve raft04-in-p<k>, raft04-p<k> e raft04-eleicao-p<k> (uma thread
     cada), ignorando as próprias mensagens (lider == i, candidato == i, eleitor == i);
  6. agenda verificar() a cada VERIFICACAO_MS.

ELEIÇÃO:
  - verificar(): dentro do monitor do nó, t = raft.tick(); se t ≠ −1 lê
    ultimoSeq/ultimoTermo e, fora do monitor, publica PEDIDO_VOTO (o estado já foi
    gravado dentro de tick()).
  - PEDIDO_VOTO de outro nó: dentro do monitor, v = raft.onVoteRequest(..., o meu
    último registo); fora do monitor publica VOTO;v.term;i;candidato;S|N. Responde
    SEMPRE (mesmo a recusar) para que um candidato obsoleto aprenda o termo atual.
  - VOTO dirigido a mim: dentro do monitor, se raft.onVote(...) devolver true →
    assumirLideranca(t) na MESMA secção sincronizada.

LÍDER:
  - assumirLideranca(t): cancela um agendamento antigo, termoLider = t,
    seq = ultimoSeq local, L e V = os do último registo do ficheiro (ou 0 se não
    houver), hb = 0, pendentes = [], e agenda enviarLote(t) com atraso 0 (um LOTE
    imediato que afirma a liderança) e depois a cada Δ.
  - onIn(msg): valida, confirma a partição e, dentro do monitor:
      t = raft.termIfLeader(); se −1 → IGNORADO e não atribui seq;
      senão calcula seq+1, L = max(L, Lmsg)+1, V.merge(Vmsg), V.tick(k), verifica
      V[k] == seq, cria o registo com termo t, grava no ficheiro e só então
      atualiza seq/L/V/log/pendentes (se a escrita falhar, nada muda).
  - enviarLote(t): dentro do monitor, se termIfLeader() ≠ t → cancela o próprio
    agendamento e sai (demitido); senão troca pendentes, lê seq e ultimoTermo e
    incrementa hb. FORA do monitor: se isolado não publica; senão publica o LOTE em
    raft04-p<k> e acrescenta a linha a hb-p<k>-n<i>.txt.
  - Heartbeats e mensagens de eleição NÃO mexem em L nem V (só o IN o faz).

SEGUIDOR:
  - onLote(msg): (ignora se isolado ou se é o próprio lote) dentro do monitor:
    raft.onBatch(termo, lider); false → IGNORADO (com o termo do lote); true →
    RECEBIDO e aplicarLote(b).
  - aplicarLote(b): para cada registo r, com m = ultimoSeq local:
      r.seq ≤ m e mesmo termo         → duplicado (ignora)
      r.seq ≤ m e termo diferente     → divergência → resolverDivergencia
      r.seq == m+1 (e mesmo termo do registo m, ou m == 0) → acrescenta
      r.seq > m+1 (lacuna)            → recuperar (TCP)
      r.seq == m+1 mas o registo m é de outro termo → recuperar (ver 6.1)
    No fim do lote (se não for um lote atrasado do mesmo termo):
      m < ultimoSeq                       → recuperar, RECUPERACAO
      m > ultimoSeq                       → divergência
      termo(m) ≠ ultimoTermo              → divergência
  - recuperar(b): pede ao líder PEDIDO m..ultimoSeq (inclui o meu último registo m
    para confirmar que coincide); se não coincidir → divergência; senão acrescenta
    m+1.. .
  - resolverDivergencia(b): inicio = 1.º seq do meu ÚLTIMO BLOCO DE TERMO; pede
    PEDIDO inicio..max(ultimoSeq, m); enquanto o 1.º registo recebido não coincidir
    com o meu (e inicio > 1), recua um bloco de termo; encontrado o ponto em que
    coincide, procura o 1.º seq d em que difere; se d ≤ m reescreve o ficheiro de
    forma ATÓMICA sem d..m (RecordFile.rewrite), regista
    TRUNCADO;p<k>;de=d;descartados=n;termos=<lista>;leituras=<sensor@temp,…>
    e aplica os registos do líder a partir de d.
    Exemplo da Figura 1: n2 tem 1(t1) 2(t1) 3(t1); o LOTE de n3 diz ultimoSeq=3,
    ultimoTermo=2 → divergência; último bloco de termo de n2 começa em 1 → PEDIDO
    1..3; o registo 1 coincide; o 3 difere → TRUNCADO de=3 descartados=1 termos=1;
    aplica 3(t2).

SERVIDOR TCP: igual ao da COMINDIR02/04 (PEDIDO <de> <até> → linhas → FIM), mas
  serve QUALQUER nó (líder ou não) e lê o ficheiro com RecordFile.range, sem
  adquirir o monitor do nó.

4.6 HeartbeatMonitor (produtor e processador)
---------------------------------------------
onHeartbeat(term, leader, hb): termo inferior → ignora; mesmo termo e hb ≤ último
→ ignora (duplicado/atrasado); termo superior → NOVO_LIDER (termo a->b, líder);
mesmo termo e salto de hb → HB_PERDIDO; se estava SUSPEITO → RETOMA. check() a
cada 200 ms passa a SUSPEITO após FATOR_TIMEOUT×Δ = 6 s sem lotes.

4.7 Producer
------------
Um HeartbeatMonitor por partição (só lê o cabeçalho dos LOTE). Antes de enviar
para p<k>, se o detetor de p<k> estiver SUSPEITO escreve
"AVISO: partição p<k> sem líder conhecido; leitura <sensor> pode perder-se" e
envia NA MESMA (a ficha exclui retenção/reenvio). Cada IN enviado é escrito em
produtor.txt (instante;p<k>;sensor;temperatura). A rajada aceita um 3.º
argumento opcional com o intervalo entre leituras.

4.8 AlarmProcessor
------------------
Subscreve raft04-p<k> de todas as partições. Por partição guarda o maior termo
visto e IGNORA lotes de termo inferior (líder obsoleto, regista IGNORADO). Trata
cada registo pelo par (seq, termo): "k:seq:termo" no conjunto de vistos. Antes de
publicar um alarme para p<j>, se o detetor de p<j> estiver SUSPEITO, escreve o
AVISO e publica na mesma.

4.9 RaftCheck <N> <pasta> [falhas.txt]
--------------------------------------
Lê no-*, estado-*, hb-*, eventos-*, monitor-*, produtor.txt (e falhas.txt) e
escreve na consola e em relatorio-raft.txt:
 1. por partição e termo: candidatos, votos de cada candidato (+ recusas), líder
    e duração da eleição (1.º CANDIDATO → LIDER), ou "VOTO DIVIDIDO" (≥2
    candidatos sem líder) / "candidato sem maioria";
 2. segurança: termos com mais de um LIDER (tem de ser 0), nós que votaram em dois
    candidatos no mesmo termo, diminuições do termo de um nó (tem de ser 0), lotes
    de termo inferior aplicados, eventos ERRO, estado-* vs último termo;
 3. tempo até ao primeiro líder, desde o ARRANQUE do primeiro nó (termo 0), e
    número de termos até haver líder;
 4. lideranças (início, fim e porquê) e LÍDERES SIMULTÂNEOS (sobreposições);
 5. com falhas.txt: para cada falha, se o nó era líder, a indisponibilidade =
    1.º LOTE de um termo superior − instante da falha, e as leituras de
    produtor.txt enviadas nesse intervalo (e quantas se perderam);
 6. leituras perdidas (produtor.txt sem correspondência no registo final de
    nenhum nó da partição; comparação por sensor@temperatura, como multiconjunto);
 7. cada TRUNCADO: quantos registos foram descartados e quantos desses existem,
    com outro seq, no registo final do líder (ou se perderam);
 8. coincidência final: seq em que os ficheiros dos nós diferem, até ao menor
    ultimoSeq;
 9. resumo dos monitores (NOVO_LIDER, SUSPEITA, RETOMA, HB_PERDIDO, IGNORADO, AVISO).

4.10 CausalCheck <N> <pasta>
----------------------------
Lê todos os no-p<k>-n<i>.txt. Verifica V[k] = seq em TODOS os registos de TODOS
os nós (incluindo registos criados por líderes de termos diferentes — é isto que
mostra que o invariante sobrevive à mudança de líder). Para a análise causal
entre partições usa, por partição, o registo mais atualizado (maior par
(ultimoTermo, ultimoSeq)) e escreve vista-lamport.txt como antes.


===============================================================================
5. CONCORRÊNCIA: SECÇÕES SINCRONIZADAS E ORDEM DOS LOCKS
===============================================================================

Threads de um nó: (a) subscrição de raft04-in-p<k> (onIn), (b) subscrição de
raft04-p<k> (onLote), (c) subscrição de raft04-eleicao-p<k> (onEleicao),
(d) verificação a cada 200 ms (tick), (e) heartbeat (enviarLote, executor próprio),
(f) servidor TCP.

Monitores:
  - monitor do nó (this): protege log, seq, L, V, hb, pendentes, termoLider,
    agendamento e o estado do último lote aplicado;
  - monitor de RaftState: todos os métodos públicos são synchronized;
  - monitor de RecordFile: todos os métodos synchronized;
  - eventLock: só para escrever no ficheiro de eventos.

ORDEM DE AQUISIÇÃO: nó → RaftState, nó → RecordFile, e (qualquer) → eventLock.
Nunca ao contrário: RaftState não chama o nó (só o Consumer de log, que vai ao
eventLock e não adquire mais nada); o servidor TCP só usa RecordFile; tick() é
chamado dentro do monitor do nó. Sem ciclos no grafo de espera → sem deadlock.
Se algum código adquirisse RaftState e depois o nó, enquanto outra thread faz nó →
RaftState, as duas podiam ficar à espera uma da outra para sempre (deadlock).

Porque é que as operações de eleição e de lote estão DENTRO do monitor do nó?
  - IN vs demissão: onIn faz termIfLeader() + atribuição do seq + escrita numa só
    secção; a demissão (onBatch/onVoteRequest/onVote com termo superior) também
    acontece dentro do monitor do nó. Logo, ou a leitura é numerada INTEIRA antes
    da demissão (com o termo antigo, legítimo naquele instante), ou já vê
    termIfLeader() == −1 e é IGNORADA. Nunca recebe um seq com o termo antigo
    depois de o nó ter adotado o novo.
  - passagem a líder: onVote → true e assumirLideranca() estão na mesma secção; um
    IN não pode ver termIfLeader() == t com seq/L/V ainda por inicializar.
  - enviarLote troca pendentes e lê ultimoSeq na mesma secção que a atribuição do
    seq → nenhum registo fica "entre" o lote e o ultimoSeq anunciado.
  - Publicações (HTTP ao IPFS) ficam FORA das secções: não bloqueiam a entrada.
  - A recuperação TCP de um seguidor é feita dentro do monitor do nó (o termo não
    pode mudar a meio da aplicação/truncagem). Custo: enquanto dura (ms em local,
    no máximo T_TCP_MS) atrasa votos e INs desse nó. Não há deadlock distribuído
    porque o servidor TCP do outro nó não precisa do monitor desse nó.

6. DECISÕES PRÓPRIAS (O QUE A FICHA NÃO FIXAVA) E PORQUÊ
===============================================================================

6.1 Verificação na "fronteira de termo" (seguidor)
  A ficha deteta divergência em 3 casos (registo com seq que já tenho e outro
  termo; o meu registo ultimoSeq com termo ≠ ultimoTermo; registos para além de
  ultimoSeq). Há um caso que escapa: o antigo líder regressa com 1..105, em que
  101..105 são do termo 1 e nunca foram publicados; o novo líder já vai no 400
  (101..400 do termo 2) e o primeiro LOTE que o antigo líder recebe traz 398..401.
  Pela regra literal, 398 é uma lacuna → recupera 106..401 → no fim o registo 401
  tem o termo certo e ninguém repara que 101..105 são diferentes. Para evitar isto:
   - a recuperação pede SEMPRE também o meu último registo m (PEDIDO m..ultimoSeq)
     e confirma que coincide com o do líder (se não coincide → divergência);
   - um registo r com seq = m+1 mas de termo diferente do meu registo m não é
     acrescentado às cegas: passa pela recuperação (1 pedido TCP por seguidor por
     mudança de líder).
  É a ideia do "prevLogIndex/prevLogTerm" do AppendEntries, mas feita pelo
  seguidor do lado da recuperação (pull), sem resposta ao líder e sem commit —
  por isso continua dentro dos limites da ficha.

6.2 Lotes atrasados: se chegar um LOTE do mesmo termo com hb ≤ ao último
  aplicado, os registos são tratados (os duplicados são ignorados), mas a
  comparação final com ultimoSeq/ultimoTermo não é feita (esse ultimoSeq já está
  ultrapassado e daria uma falsa divergência).

6.3 Na resolução de divergência o pedido vai até max(ultimoSeq, m) (o servidor
  limita ao que tem). Assim, se a "divergência" for falsa (por exemplo por causa
  de um lote atrasado), os registos coincidem e nada é truncado.

6.4 Eventos extra ARRANQUE e ISOLAMENTO: o RaftCheck precisa do instante de
  arranque de cada nó para medir o "tempo até ao primeiro líder desde o arranque
  do primeiro nó", e o ARRANQUE inclui termo e votouEm lidos do disco (mostra a
  persistência). ISOLAMENTO;inicio/fim marca o período de partição de rede.

6.5 TRUNCADO inclui também leituras=<sensor@temp,…> (depois dos campos da ficha)
  para o RaftCheck poder dizer quantas das leituras descartadas existem no
  registo final do líder com outro seq.

6.6 Rajada com intervalo opcional (rajada 300 10 100): sem intervalo, 300
  publicações demoram ~1 s e é impossível "terminar o líder durante a rajada".

6.7 IN no líder: os novos seq/L/V são calculados em variáveis locais e só são
  aplicados depois de o registo ser gravado no ficheiro (se a escrita falhar, o
  estado não fica a meio). A verificação V[k] == seq continua lá (vem da
  COMINDIR03/04).

6.8 Falha 5: com -Draft04.falha=5 a verificação V[k] == seq do líder é desligada
  de propósito, para que o erro chegue aos ficheiros e seja o CausalCheck a
  detetá-lo (com a verificação ligada, o próprio nó rejeitaria todas as leituras
  e o efeito visível seria só "leituras perdidas").

6.9 Um caso-limite que fica por resolver (boa pergunta para discussão): se o
  processador viu um registo (seq 5, termo 1) que depois é truncado, o seu Vp
  tem V[k]=5; um alarme gerado depois leva V[k]=5 para o novo líder, que só tem
  seq 4 → depois do merge e do tick V[k]=6 ≠ seq=5 → o líder rejeita esse alarme.
  É consequência de não haver commit (o processador viu um registo que não era
  definitivo). Na prática só acontece se o lote foi entregue ao processador e
  perdido para os dois seguidores.

11. DIAGNÓSTICO INICIAL (2.2) — RESPOSTAS
===============================================================================

(a) Maioria de G nós = ⌊G/2⌋ + 1; tolera G − maioria = ⌊(G−1)/2⌋ falhas.
    G = 2 → maioria 2 → tolera 0 falhas (se uma cópia falha, a outra sozinha não
    tem maioria). G = 3 → maioria 2 → tolera 1. G = 4 → maioria 3 → tolera 1, tal
    como G = 3, mas com mais um nó que pode falhar e mais mensagens: por isso se
    usam grupos ímpares (3, 5, 7).
(b) Para ser eleito são precisos 2 votos de 3. Quaisquer duas maiorias de um
    grupo de 3 têm pelo menos um nó em comum (2 + 2 > 3). Esse nó só vota uma vez
    por termo (votedFor, gravado em disco) → não pode dar o voto aos dois
    candidatos → no máximo um líder por termo. SIM, podem existir dois nós que se
    julgam líderes ao mesmo tempo, mas em TERMOS DIFERENTES: o líder antigo,
    isolado, ainda se julga líder do termo t enquanto os outros elegem um líder do
    termo t+1. O termo não impede isso; permite reconhecer o antigo como obsoleto.
(c) Sem eleição (como na COMINDIR04): o líder isolado continuaria a receber os IN
    do produtor e a atribuir seq; os outros dois só suspeitariam; os registos
    ficariam só no líder (não replicados) até a rede voltar. Com eleição por
    maioria: só o lado com 2 nós (os dois seguidores) consegue eleger um líder
    (termo t+1); o antigo continua a julgar-se líder do termo t (nunca é
    "reeleito" sozinho, mas também não sabe que foi substituído) e, como o
    produtor alcança os dois lados, os dois atribuem seq → no fim, as escritas do
    antigo são truncadas. Relação com a partição de dados p1: NENHUMA além do nome
    — p1 é a divisão dos dados por sensor; a partição de rede é uma falha de
    comunicação que, neste caso, divide o grupo de p1. p0 e p2 (outros grupos,
    outros termos) não são afetados.

12. CAIXAS "ANTES DE AVANÇAR" — RESPOSTAS
===============================================================================

[4.1 · RaftState]
- Porque é que adoptTerm repõe votedFor a 0? votedFor diz respeito ao termo
  atual; num termo novo o nó ainda não votou. Se não o repusesse, um nó que votou
  em n2 no termo 3 e passou ao termo 4 recusaria todos os candidatos do termo 4
  exceto n2 (como se já tivesse votado), e se n2 estivesse em baixo podia não
  haver maioria → eleições bloqueadas (perda de liveness).
- Porque concede o voto a um candidato em quem já votou neste termo? Para ser
  idempotente: o mesmo PEDIDO_VOTO pode chegar duas vezes (o pubsub pode entregar
  em duplicado, ou o candidato podia repetir o pedido se o VOTO se perdesse).
  Responder "S" outra vez é seguro: é o mesmo voto, não um segundo voto.
- Que sequência levaria onBatch a registar ERRO? Este nó ser LIDER no termo t e
  receber um LOTE de OUTRO líder também do termo t → dois líderes no mesmo termo.
  É impossível pela regra da maioria (votes.size() > G/2) combinada com "um voto
  por termo" persistido. Só aparece com as falhas 1 (G = 4) ou 2.
- Ficheiro temporário + ATOMIC_MOVE: garante que o ficheiro de estado nunca fica
  meio escrito (ou é o antigo ou o novo), mesmo que o processo morra a meio. O que
  falta sem forçar a escrita no disco (FileChannel.force / fsync, e fsync da
  pasta): DURABILIDADE — os dados podem estar só na cache do sistema operativo; se
  a MÁQUINA falhar (falta de energia), o nó pode voltar com um termo/voto antigo e
  votar duas vezes no mesmo termo. Com kill -9 do processo isto não acontece (a
  cache do SO sobrevive).

[4.1.3 · Arranque do PartitionNode]
- Falha entre a gravação (em tick) e a publicação do PEDIDO_VOTO: no arranque o
  nó lê termo t e votouEm = ele próprio; ninguém recebeu o pedido. Não há problema
  de segurança: o nó "votou em si" no termo t e continua a recusar outros
  candidatos do termo t; quando o prazo expirar candidata-se no termo t+1.
- Porque responde a um PEDIDO_VOTO mesmo quando recusa? Porque a resposta leva o
  termo do eleitor: um candidato obsoleto (termo menor) recebe VOTO com termo
  superior, adota-o e passa a seguidor (onVote → adoptTerm). E o candidato fica a
  saber que foi recusado (eventos).
- Três nós em termo 0 sem líder: o primeiro LOTE surge quando o primeiro prazo
  expira, mais a votação (dezenas de ms): mínimo ≈ ELEICAO_MIN_MS = 6 s, máximo ≈
  ELEICAO_MAX_MS + VERIFICACAO_MS = 12,2 s (sem voto dividido). O primeiro a
  expirar é o mínimo de 3 sorteios uniformes: valor esperado 6 + 6/4 = 7,5 s.

[4.1.4 · Líder]
- Alguma operação adquire os dois monitores pela ordem inversa (RaftState →
  nó)? Não. RaftState nunca chama o nó; o único "callback" é o Consumer de log,
  que só usa o eventLock. Se houvesse (ex.: RaftState a chamar um método
  synchronized do nó), duas threads podiam ficar em deadlock (A tem nó e espera
  RaftState; B tem RaftState e espera nó).
- Porque é que o novo líder inicializa L e V a partir do último registo? Para
  continuar a contagem: V[k] tem de continuar igual a seq (invariante V[k] = seq)
  e L tem de ser maior do que o L de todos os registos anteriores da partição
  (condição de relógio). Começando em zero, o CausalCheck mostraria "Violações
  V[k]=seq" (V[k] = 1 com seq = 3) e possivelmente violações de Lamport.
- O líder do termo 2 recebe um IN que o líder do termo 1 já tinha recebido mas
  não publicado: se o líder do termo 2 também o recebeu enquanto já era líder
  (caso do isolamento, 9(d)), atribui-lhe um seq NOVO no termo 2 → a leitura fica
  no registo final com outro seq, e a cópia do termo 1 é truncada no antigo líder
  (não há duplicado no fim). Se o IN chegou antes de o novo líder ser eleito
  (caso da falha, 9(a)/(c)), os outros nós ignoraram-no (IGNORADO) → a leitura só
  existia no antigo líder e perde-se quando é truncada.

[4.1.6 · Processador]
- (seq 7, termo 3) depois de (seq 7, termo 2): são registos DIFERENTES (o par é
  diferente) → deve tratá-lo e gerar alarme se a temperatura o justificar.
  Consequência: a contagem de alarmes pode incluir alarmes de registos que acabaram
  descartados (o (7, 2) foi truncado) e até dois alarmes para a mesma leitura (se
  (7, 2) e (7, 3) forem a mesma leitura recebida por dois líderes). Sem commit, o
  processador não tem forma de saber que (7, 2) não era definitivo.

CA1 · FUNDAMENTOS
- Definições rápidas:
  termo = número inteiro crescente e persistente que identifica uma época de
  liderança; cada termo começa com uma eleição e tem no máximo um líder.
  maioria (quórum) = ⌊G/2⌋ + 1 nós (2 de 3); duas maiorias intersectam-se sempre.
  restrição de voto = só se vota num candidato cujo último registo é pelo menos
  tão atualizado como o nosso (termo do último registo maior, ou igual e seq ≥).
  CAP: C = comporta-se como uma única cópia (cada leitura vê a última escrita
  concluída); A = todo o pedido a um nó vivo recebe resposta que não é erro;
  P = continua a funcionar apesar de a rede perder mensagens entre nós. Durante
  uma partição de rede não se consegue ter C e A ao mesmo tempo.
- Porque é que o termo garante no máximo um líder POR TERMO mas não um líder
  ativo POR INSTANTE: a garantia vem da maioria dentro do mesmo termo. Um líder
  antigo isolado não sabe que houve uma eleição num termo superior (não recebe
  mensagens) e continua a agir como líder do termo t até receber algo do termo
  t+1. Garantir "um líder por instante" exigiria arrendamentos (leases) com
  relógios, excluídos da ficha.
- Se n1 tivesse falhado em t = 15, n3 poderia ser eleito no termo 2? Não: com n2
  (falhou em 12) e n1 em baixo, n3 só tem o seu voto (1 de 3). Candidata-se nos
  termos 2, 3, 4, … sem nunca ter maioria → p1 fica sem líder e INDISPONÍVEL para
  escritas (as leituras perdem-se). Em CAP: o sistema abdica de A para não pôr C
  em risco (para n3, dois nós em baixo são indistinguíveis de uma partição de rede
  que o deixa na minoria).
- Porque é que n2, ao regressar, não volta a ser líder? Porque já existe um líder
  (n3, termo 2) que lhe envia LOTEs: n2 adota o termo 2, passa a seguidor e o
  prazo é renovado a cada lote. Mesmo que se candidatasse (termo 3), o seu último
  registo é (3, termo 1) e o dos outros é (3, termo 2): termo do último registo
  inferior → restrição de voto → recusado. E se regressasse em t = 16, antes de
  qualquer eleição? Podia ser eleito no termo 2: n1 e n3 têm (2, 1) e n2 tem
  (3, 1) — mesmo termo, seq maior → upToDate. Se o prazo de n2 expirar primeiro,
  ganha (e S02 20.4 não se perde). Se expirar primeiro o de n3, n3 pede votos com
  (2, 1): n2 recusa (n3 menos atualizado) mas n1 concede → n3 ganha com 2 votos.
- Partição de dados p1 vs partição de rede que isole n2: p1 = registos dos
  sensores com hash mod 3 = 1 (S02, S05), servidos pelo grupo de p1. A partição de
  rede é uma falha de comunicação: n2 continua a funcionar mas não troca
  mensagens com n1/n3. O termo de p1 é independente do de p0: cada partição de
  dados tem o seu grupo, os seus tópicos (raft04-p<k>, raft04-eleicao-p<k>), os
  seus ficheiros de estado e a sua sequência de termos; p0 pode estar no termo 1
  e p1 no termo 7.

CA2 · IMPLEMENTAÇÃO (ver a secção 16 para os sítios no código)
- Porque é que o estado persistente é gravado ANTES de publicar o VOTO ou o
  PEDIDO_VOTO? Porque a mensagem é uma promessa ("votei em X no termo t"); se a
  promessa sai e o nó morre antes de a gravar, ao reiniciar não se lembra dela.
  Sequência com dois líderes no mesmo termo: termo 5, candidatos A e B; n2 vota
  em A (publica VOTO) e morre antes de gravar; A tem {A, n2} → líder do termo 5.
  n2 reinicia com o estado antigo (termo 4, votouEm antigo), recebe o PEDIDO_VOTO
  de B do termo 5, adota o termo 5 com votedFor = 0 e vota em B → B tem {B, n2} →
  também líder do termo 5. Para o PEDIDO_VOTO é análogo: o candidato "votou em
  si" no termo 5; se reiniciar sem o ter gravado, pode votar noutro no termo 5.
- O nó recebe um IN no instante em que se demite: a atribuição do seq (onIn) e a
  demissão (onBatch/onVoteRequest/onVote, que chamam adoptTerm) são feitas dentro
  do MESMO monitor (o do nó). Ou o IN entra primeiro e é numerado com o termo
  antigo (legítimo naquele instante; mais tarde será truncado se o novo líder não
  o tiver), ou entra depois e termIfLeader() devolve −1 → IGNORADO. Não há
  intercalação possível. O mesmo vale para enviarLote: verifica termIfLeader()
  na secção e cancela o agendamento se já não for líder.
- Porque é que o prazo é sorteado de novo a cada eleição e a cada voto concedido?
  Se fosse sorteado só no arranque, dois nós com prazos parecidos voltariam a
  expirar juntos em todas as eleições (voto dividido repetido para sempre); um
  sorteio novo em cada eleição desempata. Renovar ao conceder um voto evita que um
  nó que acabou de votar num candidato se candidate logo a seguir e o atrapalhe
  (dá ao candidato tempo para ganhar e enviar o primeiro LOTE).

CA4 · LIMITES
- Durante o isolamento do líder em 9(d), quem leu o ficheiro do antigo líder viu
  dados que depois desapareceram. Que mecanismo do RAFT completo impediria que
  essas escritas fossem consideradas aceites? O COMMIT POR MAIORIA: o líder só
  considera um registo confirmado (e só responde ao cliente / só o expõe a
  leitores) quando uma maioria o tem (AppendEntries com resposta + índice de
  commit). O líder isolado nunca obtém maioria → nunca confirma. Para leituras,
  seria preciso também confirmar a liderança (ReadIndex) ou arrendamentos. O
  sistema ficaria CP: o lado minoritário fica indisponível (não confirma nada).
- Porque é que um seguidor isolado aumenta o termo a cada prazo e, ao regressar,
  demite um líder saudável? Isolado, não recebe LOTEs → o prazo expira →
  candidata-se (termo+1) → sem votos → o prazo expira de novo → termo+1 … Ao
  regressar, o seu PEDIDO_VOTO tem um termo maior do que o do líder → o líder
  adota esse termo e demite-se (adoptTerm). Se o seu registo estiver atrasado o
  voto é recusado e outro nó ganha a eleição seguinte; se estiver atualizado
  (sem escritas durante o isolamento) é ele que ganha — mas, em ambos os casos, o
  líder saudável já caiu → eleição desnecessária. Mecanismo do RAFT que
  evita isto: PRE-VOTE (o nó primeiro pergunta "votarias em mim?" SEM aumentar o
  termo; só avança se uma maioria disser que sim, e os nós dizem que não enquanto
  ouvem um líder válido). Também ajuda ignorar pedidos de voto durante o prazo
  mínimo após um heartbeat ("leader stickiness"/CheckQuorum).
- As leituras enviadas durante a eleição perdem-se. Se o produtor as reenviasse
  até serem confirmadas, que problema surgiria? DUPLICADOS: uma leitura pode ter
  sido aceite (por exemplo pelo antigo líder, ou a confirmação perdeu-se) e ser
  reenviada → fica duas vezes, com seq diferentes. Solução: identificador único
  por leitura (id do produtor + número de pedido) e deduplicação no líder (tabela
  de sessões de cliente, como no RAFT), com a confirmação só enviada depois do
  commit por maioria. Nada disto cabe na ficha (retenção/reenvio excluídos).

14. REFLEXÃO CRÍTICA (PONTO 12) — RESPOSTAS-GUIA
===============================================================================
(Os números entre [ ] vêm dos testes da secção 9; substituir pelos valores dos
ensaios reais com IPFS.)

ELEIÇÃO NO ARRANQUE
  Com prazos aleatórios, o primeiro nó a expirar fica sozinho durante, em média,
  alguns segundos (diferença entre o 1.º e o 2.º sorteio), muito mais do que os
  ~20–80 ms que a votação demora [eleições de 12–79 ms] → recebe os votos antes de
  outro se candidatar → quase sempre 1 termo [todas as partições: 1 termo,
  6,3–11,6 s até ao 1.º líder]. Com prazo fixo e arranque simultâneo, todos
  expiram ao mesmo tempo, votam em si próprios e recusam os outros (já votaram) →
  voto dividido, termo após termo, enquanto os relógios não se desalinharem.
  A ordem de arranque deixou de importar porque não há líder configurado: quem
  arranca mais cedo pode ganhar, mas qualquer ordem dá um líder; e um nó que
  arranca depois recebe um LOTE e torna-se seguidor.
  Relação necessária: atraso da rede ≪ Δ < ELEICAO_MIN_MS ≪ tempo médio entre
  falhas; aqui Δ = 2 s, ELEICAO_MIN = 3Δ (tolera perder 2 lotes seguidos sem
  eleição), ELEICAO_MAX = 6Δ (intervalo largo → menos votos divididos). Se
  ELEICAO_MIN_MS < Δ, um seguidor podia expirar ENTRE dois heartbeats normais →
  candidaturas constantes, demissões de líderes saudáveis e termos a subir sem
  parar (o sistema ficaria quase sempre sem líder).

O TERMO
  Prova de "no máximo um líder por termo": para ser líder no termo t, um nó
  precisa de votos de uma maioria M1 no termo t; outro precisaria de M2; M1 ∩ M2 ≠
  ∅ (2+2 > 3); um nó de M1 ∩ M2 teria de votar em dois candidatos no termo t, mas
  votedFor só é posto quando é 0 ou igual ao candidato e é persistido antes do
  VOTO → impossível. ∎
  9(d): o antigo líder, isolado, nunca recebe mensagens do termo t+1 → continua a
  julgar-se líder de t enquanto os outros elegem o líder de t+1 [RaftCheck secção
  4: LÍDERES SIMULTÂNEOS]. Ao reparar, o primeiro LOTE do termo t+1 demite-o
  (DEMISSAO, TERMO t->t+1) e os registos do termo t que não existem no novo líder
  são truncados. O termo é o que permite DECIDIR quem prevalece.
  Termo vs Lamport: semelhantes — inteiros que só crescem, viajam em todas as
  mensagens, quem recebe um valor maior adota-o. Diferentes — Lamport ordena
  EVENTOS (incrementa em cada evento, L(a) < L(b) se a → b); o termo identifica
  ÉPOCAS DE LIDERANÇA (só incrementa numa candidatura), mensagens de termo menor
  são REJEITADAS (com Lamport nunca se rejeita nada), e o termo é persistente.

CAP E PARTICIONAMENTO (tabela)
  Falha do líder (c): maioria (2 vivos) aceita escritas após a eleição; não há
    lado minoritário vivo; as escritas pendentes do líder morto perdem-se;
    termos t, t+1; durante a eleição ninguém aceita escritas → C (troca A por C
    durante alguns segundos).
  Isolamento do líder (d): maioria aceita (novo líder t+1); minoria (antigo líder)
    TAMBÉM aceita escritas nesta ficha (sem commit) → descartadas/truncadas após a
    reparação; termos t e t+1 → comporta-se como A durante a partição (aceita dos
    dois lados) e "reconcilia" deitando fora o lado minoritário — não é C em rigor.
  Isolamento de um seguidor (d): maioria (líder + 1) aceita; minoria (o seguidor)
    não aceita (não é líder: IGNORADO); nada a reconciliar além de recuperar o que
    perdeu; o seu termo sobe [2 → 6 em 40 s] e, ao regressar, demite o líder e
    provoca uma eleição desnecessária [termo 7] → C.
  Falha de dois nós (e): o sobrevivente não tem maioria → NINGUÉM aceita
    escritas; termos sempre a subir sem líder → C (indisponível).
  O lado minoritário não consegue eleger líder porque precisa de 2 votos e só tem
  1 nó. O sistema desta ficha NÃO é, em rigor, CP: o antigo líder isolado aceitou
  escritas que depois foram descartadas (um cliente podia tê-las lido). O que o
  tornaria CP: commit por maioria (AppendEntries com resposta + índice de commit)
  e responder ao cliente só após o commit (e leituras via líder confirmado). Custo:
  cada escrita espera por uma ida e volta a uma maioria (mais latência; no nosso
  desenho por lotes, até mais um Δ), e o lado minoritário fica indisponível também
  para leituras consistentes.

RESTRIÇÃO DE VOTO E TRUNCAGEM
  Protege: um nó a quem faltam registos que uma maioria tem não pode ser eleito,
  logo registos que chegaram a uma maioria nunca são truncados (na Figura 1, n1 dá
  o voto a n3 porque (2, 1) é tão atualizado como o seu). Não protege: registos
  que só o líder tinha (pendentes, ainda não publicados) ou que só uma minoria
  recebeu — sem commit, ninguém sabe que estavam "aceites". [9(a): S02 20.4 estava
  no ficheiro do líder mas não foi publicado → truncado; 9(c): 5 truncados.]
  Sem a restrição (falha 3), um nó atrasado podia ser eleito e os outros
  truncariam registos já replicados.

PERSISTÊNCIA
  Termo e voto têm de ser persistentes para que um nó reiniciado não vote duas
  vezes no mesmo termo (falha 2 → dois líderes possíveis) e não recue no termo.
  Os registos também são persistentes porque a restrição de voto compara o último
  registo: um nó que perdesse o registo ao reiniciar podia votar num candidato
  atrasado e os registos "conhecidos pela maioria" deixariam de estar protegidos;
  além disso o novo líder inicializa seq/L/V a partir do ficheiro. Na ficha
  anterior, a incarnação inc (instante de arranque) era o que distinguia, para os
  participantes, um líder reiniciado do anterior — papel parecido ao do termo,
  mas local a um processo e não persistente/partilhado.

DETETAR, SUSPEITAR E ELEGER
  Na COMINDIR04 uma falsa suspeita era inofensiva (só um evento). Agora uma falsa
  suspeita (por exemplo, o líder pausado mais do que ELEICAO_MIN_MS, GC longo ou
  rede lenta) dispara uma eleição: novo líder, demissão do antigo quando acordar,
  leituras perdidas durante a eleição e truncagem do que o antigo aceitou entretanto
  — exatamente o que se vê em 9(d). O seguidor isolado provoca uma eleição
  desnecessária porque volta com um termo maior do que o do líder e o líder é
  obrigado a adotá-lo. Pre-Vote: antes de aumentar o termo, o nó pergunta se o
  elegeriam; os outros, que ouvem o líder, dizem que não → não incrementa → não
  perturba o líder ao regressar.

LIMITES
  Leituras enviadas a uma partição sem líder [9(c): 24 numa indisponibilidade de
  7,4 s; 9(e): todas durante os 30 s] perdem-se sem vestígio (os nós vivos
  registam IGNORADO; o produtor só avisa). Para não perder nenhuma leitura aceite
  sem duplicados: o produtor reenvia até receber confirmação; cada leitura tem um
  id único (produtor + nº); o líder deduplica por id; a confirmação só é dada após
  commit por maioria; o novo líder herda os ids já vistos (estão no registo). Nada
  disso cabe no âmbito desta ficha (retenção/reenvio, commit e respostas excluídos).

15. MAIS PERGUNTAS PROVÁVEIS: TEÓRICAS
===============================================================================

P: Qual a diferença entre safety e liveness aqui?
R: Safety ("nada de mau acontece"): no máximo um líder por termo; nunca votar duas
   vezes; termo nunca diminui. Garantido SEMPRE pela maioria + voto persistente,
   mesmo com mensagens atrasadas/perdidas. Liveness ("algo de bom acaba por
   acontecer"): haver líder. Depende de uma maioria viva e ligada e de timeouts
   razoáveis (prazos aleatórios). Pelo resultado FLP, num sistema totalmente
   assíncrono não se garante liveness com falhas; o RAFT usa temporizadores
   (sincronia parcial) só para a liveness, nunca para a safety.

P: Porque é que um seguidor não assume logo a liderança quando suspeita?
R: Porque dois seguidores podiam suspeitar ao mesmo tempo e ambos atribuir o mesmo
   seq a leituras diferentes (split brain). A eleição com maioria impede isso.

P: Porque é que crash e partição de rede são indistinguíveis para os outros nós?
R: Em ambos os casos simplesmente deixam de chegar mensagens. Por isso o
   protocolo tem de ser seguro nos dois: um "morto" pode estar vivo e isolado
   (o caso do líder obsoleto).

P: O que acontece se dois candidatos se candidatarem no mesmo termo?
R: Cada um vota em si; o terceiro vota no primeiro pedido que receber (se o
   registo estiver atualizado) → esse ganha; o outro recebe o LOTE do vencedor
   (mesmo termo) e passa a seguidor. Se os votos se dividirem (p.ex. o terceiro
   estiver em baixo), ninguém ganha; os prazos expiram em instantes diferentes e há
   nova eleição num termo superior.

P: Porque é que o líder publica um LOTE imediatamente ao ser eleito?
R: Para afirmar a liderança: os outros renovam o prazo (não se candidatam), um
   candidato concorrente do mesmo termo passa a seguidor, e o produtor/processador
   ficam a conhecer o novo termo (NOVO_LIDER).

P: Porque é que o candidato precisa de incluir ultimoSeq e ultimoTermo no pedido?
R: Para os eleitores aplicarem a restrição de voto (comparar com o seu último
   registo). Compara-se primeiro o TERMO do último registo (registos de termos
   mais recentes vêm de líderes mais recentes) e só depois o seq.

P: Porque compara primeiro o termo e não o seq?
R: Um nó com mais registos mas de um termo antigo pode ter um sufixo que nunca foi
   aceite (como n2 na Figura 1: seq 3 do termo 1). O termo do último registo diz
   de que "época" é a informação mais recente que o nó tem.

P: O que é um bloco de termo e porque se recua por blocos?
R: Sequência final de registos consecutivos com o mesmo termo. Dentro de um bloco
   todos os registos vêm do mesmo líder; se o primeiro registo do bloco coincide
   com o do líder, a divergência está mais à frente; se não coincide, todo o bloco
   pode estar errado e recua-se para o bloco anterior. É mais rápido do que recuar
   um seq de cada vez.

P: Que garantias dá o pubsub do IPFS? Isso importa?
R: Melhor esforço: as mensagens podem perder-se, chegar duplicadas ou (entre
   publicadores diferentes) fora de ordem. O protocolo tolera: duplicados são
   ignorados (mesmo seq e termo), lacunas recuperam-se por TCP, mensagens de termo
   antigo são ignoradas, e votos/pedidos repetidos são idempotentes.

P: CAP — o RAFT é CP ou AP? E este sistema?
R: O RAFT completo é CP (minoria indisponível, consistência linearizável com
   commit e leituras pelo líder confirmado). Este sistema elege como o RAFT (só a
   maioria elege), mas sem commit o líder isolado aceita escritas → não é CP em
   rigor; também não é AP (as escritas da minoria são deitadas fora em vez de
   reconciliadas).

P: Porque é que um grupo de 4 não tolera mais falhas do que um de 3?
R: Maioria de 4 = 3 → tolera 1 falha, tal como 3. E com 4 uma partição 2–2 deixa
   os dois lados sem maioria (com 3 há sempre um lado com maioria).

P: O que é a "propriedade de interseção dos quóruns"?
R: Quaisquer dois quóruns (maiorias) partilham pelo menos um nó. É a base da prova
   de unicidade do líder por termo e, no RAFT completo, de que um registo
   confirmado está em qualquer maioria futura (logo no próximo líder).

Perguntas de "e se…" sobre o código:
  - E se tirasse o synchronized(this) à volta de raft.onVote + assumirLideranca?
    Um IN podia ver termIfLeader() = t entre as duas chamadas e numerar com seq/L/V
    da liderança anterior (ou não inicializados).
  - E se a publicação do LOTE fosse dentro da secção? Funcionava, mas cada IN
    ficava à espera do HTTP ao IPFS (latência e débito piores), como já se
    discutia na COMINDIR04.
  - E se o seguidor não renovasse o prazo em onBatch? Candidatava-se mesmo com o
    líder vivo → demissões constantes.
  - E se o servidor TCP adquirisse o monitor do nó? Um seguidor que está a
    recuperar (com o seu monitor) a pedir a outro que também está a recuperar a
    pedir ao primeiro → deadlock distribuído possível. Por isso só usa RecordFile.
  - Porque é que enviarLote recebe o termo como argumento? Para que um
    agendamento de uma liderança antiga nunca publique lotes de um termo
    posterior (compara termIfLeader() com o termo do agendamento).
